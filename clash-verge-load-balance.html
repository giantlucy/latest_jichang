CLASH VERGE REV / 指定节点配置

Clash Verge Rev 负载均衡：用扩展脚本建一个指定节点高可用分组

把几个想用的机场节点写进一个数组，选好负载均衡策略，再让新连接经过这个分组。配置直接放在下面，照着修改节点名就能开始试。

本文使用 Mihomo 的 load-balance，分组名里的“高可用”只是方便识别。它与主节点故障后才切备用的 fallback 不同，也不是多条线路带宽叠加。

复制配置图解操作连接对比策略选择问题排查

先配置：复制脚本，只改节点全名

在目标订阅的扩展脚本中使用以下代码。已有其他扩展逻辑时先备份，不要直接覆盖掉需要保留的内容。这里的三个节点名都是示例，需要替换成你订阅里的真实名称。

function main(config) {
  // 必须完整复制订阅中的名称，包括 emoji、空格和标点。
  const nodes = [
    "🇭🇰 香港 01",
    "🇭🇰 香港 02",
    "🇯🇵 日本 01"
  ];

  // 可选：round-robin / consistent-hashing / sticky-sessions
  const strategy = "round-robin";
  const groupName = "⚖️ 指定节点负载均衡";
  const selected = [...new Set(nodes)];

  if (selected.length === 0) {
    throw new Error("请先在 nodes 数组中填写节点名称");
  }

  const available = new Set(
    (config.proxies || []).map(proxy => proxy.name)
  );
  const missing = selected.filter(name => !available.has(name));

  if (missing.length > 0) {
    throw new Error(
      "找不到以下节点，请核对完整名称：\n" + missing.join("\n")
    );
  }

  const groups = (config["proxy-groups"] || []).filter(
    group => group.name !== groupName
  );

  for (const group of groups) {
    if (group.type === "select" && Array.isArray(group.proxies)) {
      group.proxies = [
        groupName,
        ...group.proxies.filter(name => name !== groupName)
      ];
    }
  }

  groups.push({
    name: groupName,
    type: "load-balance",
    strategy,
    proxies: selected,
    url: "https://www.gstatic.com/generate_204",
    interval: 60,
    timeout: 3000,
    lazy: false
  });

  config["proxy-groups"] = groups;
  return config;
}
本教程统一使用全局模式：保存应用后，在代理页面切换到“全局”，再在全局选择器中选中“⚖️ 指定节点负载均衡”。创建分组不等于流量已经经过它；全局模式也不等于自动接管电脑上所有程序，仍需有系统代理、TUN 或应用代理把流量交给核心。

脚本会校验节点名，替换同名分组，并把新组加入已有的手动选择组。它适用于节点直接列在 config.proxies 中的订阅。如果节点来自 proxy-providers，需要另写适配，不能直接套用这段存在性检查。

还在选择机场订阅？

查找稳定机场推荐时，先核对节点可用性、设备兼容和流量限制，付款周期按自己的用量决定。推荐列表可以作为比较入口，实际表现还要在自己的网络环境里验证。

从订阅右键菜单开始，按图设置

打开这条订阅的扩展脚本

进入订阅页面，对当前使用的订阅点右键，找到扩展脚本入口。尽量用订阅关联的脚本维护这项改动，避免直接修改下载下来的节点配置，下一次订阅更新又被覆盖。

复制真实节点名，不要凭印象手打

仍然在订阅右键菜单里选择“编辑文件”，打开订阅内容。找到 proxies 下需要使用的节点，复制对应的 name 值。外层 YAML 引号不是名称的一部分，名称内部的空格、国旗和地区后缀则要保留。

把复制的名称填进脚本顶部 nodes 数组，每个名称用英文双引号包起来，各项用英文逗号分开。如果名称本身包含双引号或反斜杠，需要按 JavaScript 字符串规则转义。这里最容易忽略的不是代码，而是“看起来一样”的空格和符号。

应用配置，切到全局模式并选择分组

保存脚本后重新应用订阅，确认客户端没有配置校验错误。接着打开代理页面，切到全局模式，选择新建的“⚖️ 指定节点负载均衡”。你若自行改了 groupName，界面里就选改名后的组。

这里要求全局模式，是为了让配置和验证路径保持一致。负载均衡本身也支持规则模式；日后切回规则模式，需要让相关规则最终指向这个组，否则那些连接仍会经过原来的分组。

看连接列表，确认多个节点真的参与了

用 round-robin 测试时，新建多个请求，观察连接详情中的代理链。先看修改前后截图，重点放在连接经过的节点名称，不要只盯着测速数字。

已经建立的连接不会因为修改策略就自动搬到另一个节点。浏览器还可能复用已有连接，所以刷新同一页面并不是很好的测试方法。可以关闭测试页面后重新打开几个不同站点，再回客户端查看新连接；不必为了验证而中断正在下载或通话的任务。

看到多条连接也不代表流量一定均分。一个连接可能只传几 KB，另一个却持续传视频；轮询分的是连接机会，不是每秒字节数。如果列表里其实只有一个健康节点可用，其余节点也不会凭空承担流量。

负载均衡策略怎么选？先轮询，再考虑出口稳定

strategy分配思路适用情况
round-robin新连接在可用节点间轮流分配验证多个节点参与工作，或接受出口变化的多连接使用
consistent-hashing按目标做一致性哈希，尽量让相同目标使用相同节点希望同一目标的出口相对稳定
sticky-sessions按源地址和目标地址维持一段时间的节点选择希望相同来源访问相同目标时保持黏着

改策略只需要修改开头的 strategy 字符串，然后重新应用配置。实际支持情况以当前 Mihomo 核心版本为准。哈希和会话黏着都不是固定 IP 承诺，节点变动或故障仍可能引起出口变化。

涉及账号登录、支付、风控严格的服务时，频繁变换出口可能增加验证次数。这样的流量可以使用相对稳定的策略，或者直接选一个合适节点。没必要把所有应用都塞进轮询组。

高可用、自动测速、故障转移不是同一个功能

fallback 按列表顺序优先使用健康节点，适合主用加备用；url-test 根据检测延迟等条件选择节点；load-balance 则按策略把连接分配出去。想要几个节点一起承担不同连接，就使用本文的负载均衡组；只想主节点坏了才换下一个，应该选故障转移。

健康检查参数，不必一上来就调得很激进

这里设置每 60 秒检测一次，单次超时 3000 毫秒，lazy: false 用于持续执行定时检测。对于少量指定节点，这是一套方便观察的起点；节点很多时，持续探测也会增加请求量。

检测地址访问成功，说明这次探测通过，不保证视频解锁、某个 AI 服务或其他业务一定可用。探测目标自身异常也可能影响判断。遇到“节点测速正常但网站打不开”，应再检查具体目标、DNS、出口限制和连接日志。

负载均衡不会让原本不可靠的节点变可靠。几个节点若共享同一条出口或上游线路，可能一起出故障；即使健康检查发现问题，已经中断的会话也可能需要重连。这套配置不提供无缝恢复保证。

配置后不生效，按现象查

提示“找不到以下节点”

先到订阅文件里重新复制名称，检查是不是选错订阅，或机场更新时改了名字。节点列表采用 proxy-providers 的配置也会触发本脚本的检查错误，这时要按提供者结构改写，而不是删掉检查后碰运气。

界面里没有负载均衡组

确认脚本已保存、关联的是当前订阅，而且重新应用后没有报错。还要检查是否有其他扩展脚本在后面覆盖了 proxy-groups。只有最终运行配置包含该组，代理页面才有东西可选。

组建好了，连接还是走旧节点

检查全局选择器是否真的选中了新组，再看那些连接是否在切换之前已经建立。若应用没有把流量交给 Clash Verge，改组也不会影响它。系统代理和 TUN 是否启用，要按应用的接管方式分别确认。

订阅一更新，原来的节点就不能用了

脚本会保留你填写的名称，不会自动猜机场改名后的节点。更新后若有名称失效，重新编辑数组即可。保持精确匹配的好处，是不会把同名地区中不想用的线路误加进来。

不想用了，怎么恢复？

先把全局入口切回原来的节点或组，停用本次扩展脚本，再重新应用订阅。若原来已有自己的脚本，恢复事先备份的版本，不要把其他定制逻辑也一起清掉。

把少量合适的节点放进去就够了

这份配置的核心只有节点数组、负载均衡策略和实际入口选择。先选两三个能用的节点，确认连接链路，再决定要不要扩充。把几十个节点全部塞进去，并不会自动得到更稳定的体验。
